# システム全体設計 — 初期案

**状態:** 提案アーキテクチャ。PR #1〜#8でスモークテスト、無料動画アダプター、単一ホストのジョブ管理、カット承認と企画会話状態を一部実装済み。Web UI・共有本番基盤は未実装。詳細は[再利用監査](./REUSE_AUDIT_2026-11-15.md)。  
**基準日:** 2026-11-15。基盤はMulmoCastフォーク。

## 1. 役割分担

~~~
[利用者: Web UI]
  依頼 / 資料アップロード / 企画承認 / カット修正 / 最終承認
            |
            v
[認証されたAPI + 制作オーケストレーター] ←→ [DB: プロジェクト・状態・履歴]
            |                            ↖ [素材ストレージ: 画像/MP4/音源]
            |
            +--> AIディレクター（企画・構成を提案）
            |        |
            |        v
            |    MulmoScript (既存DSL v1.1を原則維持)
            |
            +--> 生成ジョブキュー / 無料枠・権限・モデル選択
                       |
            +----------+-----------+
            |                      |
            v                      v
      [画像生成]               [画像→動画生成]
      MulmoCast agents         MulmoCast agents
      + 無料AI adapter         + 無料AI adapter
            |                      |
            +------画像/MP4---------+
                       |
                       v
      [既存MulmoCast: FFmpeg編集・字幕・BGM]
                       |
                       v
                 [最終MP4]
~~~

### なぜオーケストレーターが必要か

MulmoCastは生成と編集を実行できる。ただしWebサービス向けの「人が承認するまで停止」「長時間の生成待ち」「モデルごとの日次無料枠」「利用者別の履歴・アクセス制御」は別の関心事。この管理を追加する。**生成や編集の内部処理を再実装する意図ではない。**

### 用語

- **DSL:** 動画の内容をプログラムに伝えるための書き方。今回のDSLはJSON形式のMulmoScript。
- **beat:** MulmoScriptの1カット。
- **オーケストレーター:** 制作の各工程と承認待ちを進める司令塔。
- **adapter / agent:** 個々の生成AIとの入力・出力変換を担当するプログラム。
- **ジョブキュー:** 混雑時に処理を順番待ちにして、失敗や再開を管理する仕組み。

## 2. ユーザー体験と制作ステージ

| ステージ | AI/システムが行う処理 | 人間の操作 |
|---|---|---|
| 依頼 | 内容を保存し、参考素材を整理する | テーマ、用途、尺、SNS、素材等を登録 |
| 企画・演出 | 既存GraphAI/LLMが**1つの企画**とカット割りを提案し、通常の文章で修正 | チャットで修正、承認。ChatGPT等の企画文をペーストしてもよい |
| 絵コンテ確定 | MulmoScriptの有効性・各カットの動作指示を検証 | 必要に応じてカット割りを確認 |
| 静止画生成 | 各beatの画像生成（参考画像を利用できる場合は活用） | 全体または個別に承認・差し戻し |
| 画像→動画 | **承認された各静止画を動画AIに送る** | 個別プレビュー、再生成・承認 |
| 編集 | 承認済みクリップをMulmoCastで結合 | 字幕/BGM/順序などを確認 |
| 完成 | 最終MP4、設定、履歴を保存 | 承認、ダウンロード |

SNS出力の第一候補は9:16の縦動画。後から16:9、1:1などを増やせる設計にする。SNS投稿の自動化は初期必須ではない。

AIディレクターの出力では、単なる文章説明に加えて、各カットの「画面で見せたいもの」「静止画生成指示」「動画化時の動き」「想定秒数」「共通の見た目」「必要素材」「実現性」を持たせる。連続性を保つため、人物、ロゴ、商品、場面の共通参照も想定する。

## 3. MulmoCastから再利用する機能

| `src/actions/image_agents.ts` | 画像/動画の前処理、参照画像・開始/終了フレームの解決 |

## 5. データの境界

- **MulmoScript:** 何を映すか。タイトル、カット、指示文、長さ、参照素材、BGMなどの制作仕様。
- **制作管理DB:** いまどこまで進んだか。誰がいつ承認したか、どのモデルを試したか、エラー・待機理由。
- **素材ストレージ:** 実際のアップロード写真、生成PNG、各MP4、最終MP4、編集用音源。
- **生成先のレジストリ:** モデルの機能、許可条件、無料枠、利用可否。DSLの中に恒久的に埋め込まない。

仕様と状態を分離する詳細は [DSL_AND_DATA.md](./DSL_AND_DATA.md)。

## 6. 主要データモデル（初期案）

- `projects`: プロジェクトID、作成者、タイトル、組織、状態、入力条件
- `script_revisions`: MulmoScript本文、バージョン、承認者、作成日時
- `shots`: beat ID、順番、現在の段階、承認された画像・動画ID
- `assets`: 素材ID、種別、保存先、権利情報、内容ハッシュ、サイズ、所属
- `generation_jobs`: リクエストID、カットID、モデル、attempt、状態、再試行条件、エラー分類
- `approvals`: 対象リビジョン、承認者、承認/差し戻し、理由
- `provider_usage`: 利用枠、利用量（取得可能な範囲のみ）、最終更新・根拠
- `audit_events`: アクセス、操作、モデル実行、出力、設定変更の履歴

具体的なDB製品とスキーマは、最初の無料AI接続試験後に決定する。

## 7. ジョブの実行方式

生成時間が長い処理をブラウザの通信で待ち続けさせない。

1. APIでジョブを登録し、サーバが受付IDを返す。
2. プロバイダー利用可能性と権限・無料枠を検査。
3. 実行可能ならキューからワーカーへ渡す。承認待ちなら実行しない。
4. ワーカーは必要な素材を読み、MulmoCastや接続先AIを実行。
5. 成功なら素材を保存し、同じジョブIDを二重適用せず結果を確定。
6. 失敗なら種類ごとに「別モデル」「後で再試行」「人が対応」のいずれかへ分岐。
7. Web UIは保存された状態を表示し、再読み込み後も継続できる。

**状態の永続化**と**冪等性**が必須。承認リビジョンが更新された後に古いジョブが完了しても、新しい承認結果を上書きしてはいけない。

## 8. カットの再生成と依存関係

画像だけ差し戻したとき：
- そのカットの画像を新しく生成する。
- **その画像を入力にした動画クリップだけ**無効化して再生成する。
- 無関係なカットの画像や動画は保持する。
- 完成動画は、必要なクリップが揃ってから再編集する。

動画の動きだけ差し戻したとき：
- 静止画は保持し、動画生成だけ再実行する。

全体のスタイルを変更したとき：
- 複数カットへ影響しうるため、どの画像・動画が影響するかを表示し、再生成前に承認を得る。

キャラクターや舞台などを別カットから参照している場合は依存関係を記録し、**影響を受けるカットだけ**再生成候補にする。生成済みクリップは履歴として保存し、古い成果物を無条件に消さない。

## 9. 実行環境の考え方（未決定）

候補は、静的フロントエンド + 認証API + DB/オブジェクトストレージ + 動画処理ワーカー。Cloudflare Pages/Workers・D1・R2などは候補であり確定ではない。

- Cloudflare Workers単体にCPU負荷の大きいFFmpegやGPU動画生成をそのまま置けるとは想定しない。生成・レンダリングは適切な実行環境へ分離する。
- GitHub Actionsは**現段階ではCI/スモークテスト用途**。本番制作のジョブ基盤にするなら利用規約・実行時間・同時実行数・無料枠・認証情報の取り扱いを検証する。
- 無料のGPU実行環境は可用性・規約・モデル配布ライセンスが条件。検証済みでないものを本番前提にしない。
- Web UIと生成処理を分離すれば、無料AIが使用不可でも企画閲覧や編集は継続できる。

## 10. 受け入れ品質と観測

- 初期の書き出しはSNS縦型MP4を想定。尺・fps・解像度・音声トラックなどはFFprobeで機械検査。
- モデルの出力の見た目は人による承認を必須とし、機械評価のみで完成扱いしない。
- カットごとのモデル・プロンプト・乱数シード（提供時）・生成時刻・所要時間・失敗理由を記録。
- 主要指標：成功率、画像→動画成功率、待機時間、1本あたり生成回数、利用枠、承認までの再生成回数。
- ログにAPIキー、利用者の私的写真、認証トークンを出力しない。
