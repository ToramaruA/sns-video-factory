# 無料運用・安全性・利用条件・障害対応

**状態:** 運用上の原則を定義。各プロバイダーの無料枠・規約の適合は未検証。

## 1. 最優先要件：勝手に課金しない

**2026-11-15追加:** 無料Tierのある公式APIは利用してよい。既存MulmoCastのGraphAI/LLM Agentを優先して再利用する。無料APIと有料APIの違いは**モデル名だけでなく、実際の契約Tier・接続経路・アカウント設定**で確認する。有料Tierへの自動移行や既定OpenAIへのフォールバックを禁止。元MulmoCastの `llmPair` は無指定時にOpenAIになるため、Web APIからは無料許可リストを通らない設定を拒否する。

**無料APIに入力するデータ:** 提供元のプライバシー条件をユーザーへ説明する。Gemini APIの無料枠では入力内容がサービス改善に使われ得るため、未公開の写真・顧客情報等を送る前に利用条件の確認と必要な同意が必要。参考：[Gemini公式料金・Tier](https://ai.google.dev/gemini-api/docs/pricing)、[Groq公式無料Tier](https://console.groq.com/docs/billing-faqs)。

ChatGPT/Claude等の外部AIで相談した内容を貼り付ける使い方には、特殊な書き出し形式を要求しない。

原則は**fail closed（不明なら生成を実行しない）**。

- 料金が不明なAPIは自動実行しない。
- 有料APIへの自動フォールバックは禁止。
- 「試用クレジットが残っている」だけのサービスを「継続無料」として登録しない。
- モデル名だけではなく、**実際の接続経路**（有料API、無料API、利用規約に合うGPU環境、ローカル実行等）まで確認する。
- 秘密鍵・課金設定のある接続先は運営者のみが登録・変更できる。
- APIキーをMulmoScript、クライアントJS、GitHubの公開リポジトリ、ログへ埋め込まない。
- 無料枠が不明なまま「残り〇回」と表示しない。
- 手動で将来有料プランを許可する場合も、**別の明示的な仕様変更・管理者承認・上限設定が必要**。初期版は有料モードを作らない。

MulmoCastの既定の生成プロバイダーには課金可能なサービスが含まれる（`src/types/provider2agent.ts`）。**APIキーなしのローカル素材結合テストの成功は、有料APIの呼び出し防止が完成したことを意味しない。**

### 本番導入前の必須テスト

- 有料の接続先しかない状態ではジョブが始まらない。
- 誤ったモデルID・設定を入力しても有料APIへ流れない。
- 接続先の利用枠不明・失敗・ネットワーク切断時に無限再試行しない。
- 料金発生が疑われるログ・エラーでも安全側に止まる。
- 画像/動画生成なしの「既存MP4結合」モードでは生成サービスへの通信が発生しないことを検査する。

## 2. 生成先の採用基準

**モデル名の列挙ではなく、利用経路ごとに検証する。**

| 判断項目 | 具体的な確認 |
|---|---|
| 継続無料か | 初回特典だけでないか。日次/週次枠、継続条件 |
| 自動化可能か | 公式APIや許可された自動利用経路があるか。UI自動操作が禁止されていないか |
| SNS宣伝に使えるか | 商用利用、広告・宣伝利用、出力物の権利・クレジット条件 |
| 入力への対応 | 画像→動画、参考画像、参考動画、開始/終了フレーム、必要サイズ |
| 出力品質 | 動き、人物・ロゴの一貫性、破綻率、透かし、解像度 |
| 実用性 | 生成時間、同時実行、レート制限、容量、失敗率 |
| 安全性 | アップロードした写真・動画の取扱い、保存・再学習、第三者公開 |

**Wan・Hunyuan等はモデルの名前であって、無料・合法・無制限のAPIが存在する保証ではない。** Hugging Face Spacesや無料GPU環境も規約・枠・停止頻度を確認する。未検証のUI自動操作には頼らない。

各候補について、確認日・一次情報URL・実際に通した短い動画・成功率・無料枠を記録したうえで使用可能にする。

## 3. 無料枠の扱いと利用人数

**ユーザー人数に固定上限を設けない。** AI実行リソースに限りがあるので、以下の方針で制御する。

- 全体の最大同時生成数・接続先別の同時生成数を設定可能にする。
- 同じ人が大量の生成を独占しないよう、初期版は単純な順番待ちを基本とし、必要なら公平性制御を追加する。
- 回復時刻が取得できるなら表示する。取得不可なら「回復時刻は不明」と表示する。
- 外部無料枠の厳密な残量が取得できない場合は、保守的な推定値として表示し、**確定値と区別**する。
- 失敗したジョブは利用枠を消費した可能性がある。二重送信を防ぎ、提供先が対応する場合は冪等性キーを使う。
- 生成しなくても閲覧・編集・承認・既存MP4再編集ができるようにする。

### UIの注意書き案

> 無料のAI生成枠は利用状況により不足することがあります。生成枠が不足した場合は順番待ち、または一時停止になります。再開時刻はサービスによって異なり、確認できない場合があります。承認済みの画像・動画は保持されます。

これは現在の運用案であり、実際の自動再開が保証されたという意味ではない。

## 4. 画像生成・動画生成の失敗分類

| エラー | 方針 |
|---|---|
| 一時的なサーバ障害 | 制限付き再試行。連続失敗時は一時停止 |
| 無料枠超過 / 429 | 回復条件を記録。安全なら別の無料AIへ。なければ待機 |
| 画像→動画未対応、参照動画未対応 | そのモデルには送らず、対応するモデルへ。なければ利用者へ通知 |
| 入力の利用規約違反・著作権等 | 自動的に別サービスで規約回避しない。人間の確認へ |
| 認証失敗 | 運営者へ通知。利用者にキーを見せない |
| 内容・形式が不正 | 自動再試行せず入力修正を求める |
| 料金発生の恐れ | 即停止。接続の可用性を再確認する |

別モデルへ切り替える際、参照画像や動作指示を**無断で省略しない**。必須機能がなければ生成せず待機する。

## 5. アクセス制御とチーム利用

Web公開時に必要な基本要件：

- ユーザー認証は必要。**不特定多数に無料生成枠を公開しない。**
- 初期は1チームの共有作業空間を想定し、将来メンバー追加に対応できる設計。人数上限は設けない。
- アカウントごとのログインを第一候補とする。組織共通メールをログインに使う方法は検討可能だが、操作履歴・アクセス停止・監査の観点から共通パスワードには依存しない。
- 管理者だけがモデル・キー・無料枠設定を変更できる。
- プロジェクト閲覧・編集・承認・削除の権限を分けることを検討する（最初のUIは単純でもサーバ側で検査）。
- 利用者が生成先のAPIキーを直接持つ必要はない。

## 6. 素材・情報の保護

- アップロードできる画像/動画の拡張子、実際のMIME型、サイズ、長さを検査する。
- 生成前に許可していない外部URLやプライベートIP、サーバ内ファイルの参照を拒否する（SSRF / パストラバーサル対策）。
- ユーザー入力や生成AIが出したHTML/コードは信頼しない。既存MulmoCastにはHTML/Remotion等の描画機構もあるので、不必要な機能は最小権限・隔離環境で扱う。
- 一時ファイル、素材、出力物、API利用ログに保存期限・削除手順を設ける。
- ストレージを公開読み取りにしない。配布には認可された期限付きURL等を用いる。
- APIキーはサーバの秘密情報管理機構に置く。GitHub Actions利用時はSecretsの読み取り範囲やPRからのアクセスを制限する。
- 生成先のサーバへ素材を送るときは、本人が把握できる説明と利用規約の確認が必要。

## 7. 権利関係

- MulmoCastのフォークは **AGPL-3.0-only**。利用者へのソース提供等、該当条件を守る。具体的な公開形態は実装前に確認する。著作権表示とライセンス文を削除しない。
- 参考写真・動画・人物の肖像、音楽、ロゴ等について、アップロード者が必要な使用権を持つことを求める。
- 無料モデルの**重みのライセンス**と、**それをホストするサービスの利用規約**は別々に確認する。
- 音楽/BGMは使用許諾・商用利用・SNS配信の条件を確認する。無料音源でも無条件利用可能とは限らない。
- 参考動画の動き転写は、権利問題と生成AIの対応可否の双方が必要。

## 8. サービス運用上の制限

無料枠はAIだけの話ではない。

- Webホスティング、DB、動画のストレージ量・転送量
- GitHub Actionsの無料実行分・並列処理・保持期間
- 長時間動画生成やFFmpegのCPU時間
- キュー・通知・ログ保存の利用量

公開前に無料枠上限と超過時の挙動を検証し、利用者向けの注意書きへ反映する。

特にフォーク元のGitHub Actionsは大規模なCIが存在する。**毎PRの全量CIが重すぎるなら、関連テストに絞る変更を別PRで検討**する。必要な検証を無条件に無効化するのではなく、費用対効果で調整する。

## 9. 監視・障害対策

最低限のイベントとして、ジョブ受理、開始、終了、再試行、無料枠待機、モデル切替、承認/差し戻し、エラーと出力ファイルの検証結果を記録する。

- 障害後の再起動で進行中ジョブが無制限に重複実行されない。
- 承認済み素材が生成失敗で失われない。
- サービスが止まっても進捗がDBから復元できる。
- 自動再試行上限と手動再開の導線を設ける。
- 運営者が生成を一括停止できる**緊急停止スイッチ**を持つ。
